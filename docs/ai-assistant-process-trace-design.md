# HomeOps AI 助手思考与工具执行过程追溯设计

> 日期：2026-11-14  
> 状态：已实现（2026-11-14）  
> 参考：Insight 的 Agent 过程数据处理方式，以及 DSH 的过程区与正式回复分层展示方式。  
> 本文记录目标设计与落地结构；后端目标测试、前端目标测试、类型检查和生产构建均已通过。

## 1. 背景与目标

HomeOps 当前已经能从 ADK 事件中识别 thinking、function_call、function_response 和普通文本，但展示与追溯仍不完整：

- thinking 只触发“思考中…”文案，具体内容没有显示；
- 工具调用只显示临时状态，工具响应只有名称，没有参数结果和最终状态；
- 业务库虽然已有 thinking 和 tool_calls 字段，但历史回放只恢复正式回复；
- 当前工具记录缺少稳定 id、结果和状态，无法可靠配对调用与响应；
- 流式过程与正式回复的展示没有形成统一的消息结构。

相关现状见[后端事件转换](../backend/ai_assistant/services.py#L38-L58)、[消息记录](../backend/ai_assistant/views.py#L94-L115)和[前端历史转换](../frontend/web/src/views/ai-assistant/index.vue#L178-L197)。

本期目标是：

1. 将思考、工具执行过程和正式回复作为一条助手消息的三个独立部分。
2. 消息顶部提供“思考与执行过程”折叠区，**默认收起**，展开后可查看实时增量。
3. 正式回复始终在折叠区下方独立展示，不受过程区开合影响。
4. 回答完成后，过程区不消失；切换会话、刷新页面或重新进入后仍可回看。
5. 正式回复下方显示本回答使用过的工具图标，点击图标可展开并定位到对应调用。
6. 流式消息和历史消息复用同一套数据结构与展示组件，避免完成后换成另一套 UI。

## 2. 展示方案：DSH 风格的分层消息

### 2.1 默认折叠状态

每条有过程数据的助手消息采用以下结构：

```text
┌─ AI 助手 ───────────────────────────────────────────┐
│ ▸ 🧠 思考与执行过程        2 次工具调用 · 已完成     │  ← 默认收起
├──────────────────────────────────────────────────────┤
│ 正式回复的 Markdown 文本……                           │  ← 始终独立显示
│                                                      │
│ 使用工具  [服务器状态图标] [搜索图标]                 │  ← 永久保留
└──────────────────────────────────────────────────────┘
```

折叠区是一行摘要，不占用大面积空间。摘要随实时事件变化：

| 当前状态 | 摘要示例 |
| --- | --- |
| 尚未收到过程事件 | `准备中…` |
| 正在接收 thinking | `正在思考…` |
| 正在调用工具 | `正在调用 get_server_status` |
| 工具完成、等待正文 | `工具调用完成，正在整理结果…` |
| 本轮完成 | `思考与执行过程 · 2 次工具调用` |
| 工具返回错误 | `1 次工具调用异常` |
| 流异常中断 | `过程未完整结束` |

只有 thinking 或 tool_calls 至少一项存在时，才显示过程折叠区。纯文本问答不增加多余 UI。

### 2.2 展开后的实时过程

```text
┌─ AI 助手 ───────────────────────────────────────────┐
│ ▾ 🧠 思考与执行过程                       正在执行…  │
│ ┌─ 思考过程 ──────────────────────────────────────┐ │
│ │ 用户询问 backend，需要先查询服务器状态……         │ │
│ └─────────────────────────────────────────────────┘ │
│ ┌─ 工具调用 #1 ───────────────────────── 调用完成 ✓ │ │
│ │ get_server_status                                │ │
│ │ 调用参数                                         │ │
│ │ { "server_name": "backend" }                     │ │
│ │ 返回结果                                         │ │
│ │ { "status": "success", "state": "running" }      │ │
│ └─────────────────────────────────────────────────┘ │
├──────────────────────────────────────────────────────┤
│ 正式回复的 Markdown 文本……                           │
│ 使用工具  [服务器状态图标]                            │
└──────────────────────────────────────────────────────┘
```

展示规则：

- 折叠区默认关闭，**收到 thinking 或工具事件时不自动展开**，避免打断用户阅读。
- 用户主动展开后，thinking 和工具记录继续实时更新，不需要等待回答完成。
- thinking 使用普通等宽或次级文本样式，保留换行，不渲染为正式回答的 Markdown。
- 每次工具调用单独成卡片，显示名称、运行状态、调用参数和返回结果。
- 参数与结果使用格式化 JSON；长内容限制展示高度并内部滚动，完整数据仍保留。
- 正式回复不参与折叠，流式正文始终显示在过程区下方。
- 过程区展开状态是前端 UI 状态，不写数据库；同一消息从流式切换到完成状态时保持用户的展开/收起选择。

### 2.3 回答完成后的追溯

回答完成后：

- 折叠区保留在原消息顶部，不自动关闭，也不自动消失；
- 默认摘要变为“思考与执行过程 · N 次工具调用”；
- 用户之前已展开则保持展开，之前收起则保持收起；
- 切换会话再回来、刷新页面后，仍从业务历史恢复相同内容；
- 历史消息同样默认收起，展开行为与实时消息一致。

不再采用 Insight 那种“回答完成后右侧过程面板自动关闭”的方式，也不建议同时维护右侧面板和消息内过程区两份状态。

### 2.4 正式回复下方的工具图标

正式回复下方增加一行“使用工具”图标：

- 按工具名称去重，同一工具多次调用只显示一个图标，并附带 `×N`；
- 当前 `get_server_status` 可映射为服务器/监控图标，未配置的工具使用通用扳手图标；
- 图标 tooltip 显示工具中文名、调用次数和聚合状态；
- 任意一次调用失败，图标显示红色状态点；全部成功则显示正常状态；
- 点击图标后展开顶部过程区，并滚动到该工具的第一次调用；重复调用仍在过程区中逐条保留；
- 图标只是过程详情的快捷入口，不替代完整工具记录。

建议工具显示名与图标集中配置，前端消息组件不硬编码大量工具判断：

```text
get_server_status → 服务器状态查询 / lucide:server
未知工具           → 原始工具名 / lucide:wrench
```

## 3. 数据结构设计

### 3.1 复用现有消息字段

当前 ChatMessage 已包含 content、thinking 和 tool_calls，见[业务消息模型](../backend/ai_assistant/models.py#L23-L36)。本期建议继续复用这三个字段，不新增过程表：

| 字段 | 内容 |
| --- | --- |
| `content` | 正式回复，不包含 thinking 和工具 JSON |
| `thinking` | 本轮 ADK 明确标记为 thought 的完整文本 |
| `tool_calls` | 有序的工具调用记录数组，包含参数、结果和状态 |

这种方式可以直接支持现有历史数据，也不需要因为工具 JSON 增加字段而执行数据库迁移。

这里的“思考过程”仅指模型/供应商通过 ADK `Part.thought` 明确返回的内容，不声称获取或保存模型未对外提供的内部推理。

### 3.2 工具调用记录

新产生的工具记录统一为：

```json
{
  "id": "call_1",
  "name": "get_server_status",
  "args": {
    "server_name": "backend"
  },
  "result": {
    "status": "success",
    "state": "running",
    "cpu": "35%"
  },
  "status": "success"
}
```

字段约定：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 本轮助手消息内的稳定调用标识；优先使用 ADK FunctionCall ID |
| `name` | string | 工具名称 |
| `args` | object | 调用参数；缺失时使用空对象 |
| `result` | object，可选 | FunctionResponse 的返回内容；未收到响应时不存在 |
| `status` | string | `running`、`success`、`error` 或 `incomplete` |

状态语义：

- `running`：已收到调用，尚未收到响应；只应出现在实时 SSE 中；
- `success`：收到正常工具结果；
- `error`：工具结果明确包含错误，例如 `error` 字段或 `status=error`；
- `incomplete`：整轮结束时仍没有匹配到工具结果，结果未知，不能误记为成功或取消。

生成与匹配规则：

1. ADK 有调用 ID 时直接使用；没有时按本轮顺序生成 `call_1`、`call_2`。
2. 工具响应优先按响应 ID 配对。
3. 响应没有 ID 时，从后向前寻找同名且仍为 `running` 的调用。
4. 找不到原调用时补建一条记录，避免丢失工具响应。
5. 同一个 ID 的 `tool_response` 更新原记录，不能新增重复调用。

### 3.3 历史数据兼容

现有数据库中可能已有仅包含 name 和 args 的旧工具记录，前端必须进行归一化：

- 缺少 id：生成仅用于渲染的 `legacy-{messageId}-{index}`；
- 缺少 args：按空对象处理；
- 缺少 result：不展示结果区域；
- 缺少 status：显示中性的“历史调用记录”，不能伪装成成功；
- 后端新数据仍必须写完整结构，旧数据不要求立即批量迁移。

### 3.4 消息标识

建议消息历史 API 补充已有主键 `id`，并在 `done` 中返回最终助手消息。数据库已有该主键，因此只需调整序列化输出，不需要新增字段。

前端另外保留 `uiKey` 作为气泡渲染和折叠状态的稳定键；收到 `done` 替换为数据库消息时，只更新业务 ID，不更换 `uiKey`。

## 4. 后端处理设计

### 4.1 用本轮收集器替代“先把 SSE 编码、再解析回来落库”

当前记录包装器会把自己刚生成的 SSE 字符串再次解析，见[记录流程](../backend/ai_assistant/views.py#L83-L115)。本期建议引入每轮独立的结构化收集器：

```text
ADK Event
   ↓
TurnStreamProcessor.process(event)
   ├─ 更新 content / thinking / toolCalls
   ├─ 输出结构化 StreamEvent，供 SSE 序列化
   └─ 本轮结束后生成 TurnResult
          ↓
     持久化助手消息
          ↓
     发送 done + 最终助手消息
```

收集器负责：

- 分离 thinking 与正式回复；
- 防止 Partial 增量和最终聚合文本重复；
- 创建、配对和更新工具记录；
- 聚合本轮最终 content、thinking、tool_calls；
- 在结束时把未配对的 running 调用标记为 incomplete。

这样可以避免 SSE 字符串成为内部数据传递格式，也让单元测试不必构造和解析 HTTP 帧。

### 4.2 Partial 文本去重必须先验证 Python ADK 行为

参考项目只发送 Partial 文本，非 Partial 聚合正文用于 ADK 自身历史和工具执行。HomeOps 不能直接照抄这一条件，因为当前 Python Runner 调用没有显式指定流式模式。

实施前需要：

1. 确认当前 `google-adk==2.11.0` 的 RunConfig 和 StreamingMode 用法；
2. 明确启用所需的 SSE 流式模式；
3. 分别采集普通文本、thinking、工具调用三轮事件的 `event.partial` 和 Part 内容；
4. 验证 LiteLlm 是否把供应商 `reasoning_content` 转为 `Part.thought`；
5. 再确定非 Partial 文本的兼容兜底，防止旧路径或非流式供应商完全没有正文。

正常流式路径只把 Partial 文本作为前端增量；最终聚合文本用于校验和 ADK 历史，不能无条件再次追加。

### 4.3 done 改为“落库成功后的权威结果”

当前 done 只包含 token 数。建议调整为：

```json
{
  "total_tokens": 123,
  "assistant_message": {
    "id": 42,
    "role": "assistant",
    "content": "正式回复",
    "thinking": "完整思考文本",
    "tool_calls": [],
    "created_at": "..."
  }
}
```

目标顺序：

1. ADK 流正常完成；
2. 收集器生成最终结果；
3. 助手消息及过程数据成功落库；
4. 再发送一次 `done`；
5. 前端用 done 中的消息校准本地临时消息。

如果落库失败，应记录完整服务端日志并发送 error，不能继续发送代表“已完整保存”的 done。前端即使收到 EOF 但没有 done，也必须按失败收尾，不能永久 loading。

### 4.4 建议的 SSE 事件负载

| 事件 | 负载 |
| --- | --- |
| `session` | `{ "session_id": "..." }` |
| `thinking` | `{ "detail": "思考增量" }` |
| `tool_call` | 完整工具记录，status 为 running |
| `tool_response` | 同 id 的完整工具记录，包含 result 和最终状态 |
| `text` | `{ "detail": "正式回复增量" }` |
| `done` | `{ "total_tokens": 123, "assistant_message": { ... } }` |
| `error` | `{ "message": "可展示的错误信息" }` |

thinking/text 暂时沿用现有 `detail` 字段，减少无关协议变更；工具事件改为完整记录是本期必须的协议增强。

## 5. 前端状态与组件设计

### 5.1 消息模型

页面层助手消息建议统一为：

```text
ChatMessage
  ├─ uiKey                 稳定渲染键
  ├─ id                    数据库消息 ID（done/历史返回后存在）
  ├─ role
  ├─ content               正式回复
  ├─ thinking              完整思考文本
  ├─ toolCalls             工具记录数组
  ├─ loading               仅本地实时状态
  └─ processExpanded       仅本地 UI 状态，默认 false
```

API 的 snake_case 字段在 API 适配层或消息归一化函数中转换为页面使用的 camelCase，流式和历史消息必须走同一个归一化入口。

### 5.2 推荐组件拆分

```text
AssistantMessageContent
  ├─ AgentProcessDetails       顶部折叠区
  │    ├─ ThinkingSection      思考文本
  │    └─ ToolCallItem[]       参数、结果、状态
  ├─ MarkdownContent           正式回复
  └─ ToolUsageIcons            底部工具图标与跳转
```

父页面只负责接收事件和更新消息，具体折叠、JSON 格式化、图标映射和定位逻辑放入子组件，避免继续把所有展示逻辑集中在页面文件中。

### 5.3 实时事件更新

- `thinking`：追加到当前助手消息的 thinking；
- `tool_call`：按 id 新增或更新记录，状态为 running；
- `tool_response`：按 id 合并 result/status，不新增重复记录；
- `text`：只追加到 content；
- `done`：用落库消息更新 content/thinking/toolCalls，保留 uiKey 和 processExpanded；
- `error`、网络异常、取消和 EOF：统一结束 loading，保留已收到的部分内容并明确标记未完成；
- 所有事件通过当前请求与消息 uiKey 的绑定写入，不能仅靠全局 streamStatus 判断目标消息。

### 5.4 滚动与折叠交互

- 默认折叠时只更新摘要，不自动展开，不强迫聊天区滚动到过程详情；
- 用户展开后，如果过程区自身已接近底部，可随实时事件滚动到底部；
- 用户手动向上查看历史过程后，不强制拉回底部；
- 点击底部工具图标时，展开过程区并定位目标调用；
- 完成、切换会话或历史替换消息对象时，不得重置用户已有的展开状态。

## 6. 持久化边界与追溯范围

### 本期保证

- 成功完成的回答：正式回复、完整 thinking、工具参数、工具结果和最终状态全部随助手消息保存；
- 历史接口返回这些字段；
- 页面刷新后可以恢复并展开查看；
- 删除会话时，业务消息中的过程数据随现有关联一同删除。

### 本期不承诺

- 不记录“模型未通过 ADK 输出”的隐藏推理；
- 不把工具执行日志等同于运维审计日志；
- 当前字段按“思考区 + 工具有序列表”分组展示，不能还原 thinking 与工具之间每一次精确交替的时间线；
- 取消或异常后的部分助手消息如何入库，沿用现有生命周期问题另行设计，不能将未完成过程伪装成完整结果。

如果后续需要严格审计每一次事件的顺序、时间和来源，再增加独立 MessageEvent/ToolExecution 表；不建议在本期为了展示需求提前引入更复杂的事件表。

## 7. 安全与容量约束

追溯意味着数据会长期保存，不能只考虑实时展示：

- 工具参数和结果在进入 SSE 与数据库前，应按工具定义做字段白名单或脱敏；
- 不保存 API Key、Token、Cookie、连接密码及服务端堆栈；
- 工具错误返回给前端时使用可读摘要，详细异常只写服务端日志；
- 对 thinking、args、result 设置可配置的大小上限和截断标记，避免单条消息无限增长；
- 原始工具结果仍可能包含不可信文本，界面按纯文本/JSON 展示，不渲染其中的 HTML 或指令。

## 8. 推荐实施顺序

1. **事件采样与协议确认**：验证 Python ADK 流式模式、partial、thought、工具 ID 和响应结构。
2. **后端收集器**：完成文本去重、工具配对、状态聚合和结构化单元测试。
3. **持久化与 done**：保存完整过程，done 返回最终助手消息，处理落库失败。
4. **前端消息归一化**：统一流式/历史结构，兼容旧工具记录。
5. **消息分层组件**：实现默认折叠的顶部过程区、独立正式回复和底部工具图标。
6. **历史与交互收尾**：保持展开状态、图标定位、长内容滚动和请求终态清理。
7. **联调验收**：覆盖普通问答、thinking、单/多工具、异常、历史刷新和旧数据。

## 9. 验收标准

| 场景 | 必须满足 |
| --- | --- |
| 纯文本回答 | 不显示过程折叠区和工具图标，正文正常流式显示。 |
| 只有 thinking | 默认只显示折叠摘要；展开可看到实时增量，完成后仍可回看。 |
| 单次工具调用 | 过程区依次显示 running 和最终状态，参数与结果完整，正文不重复。 |
| 多次/重复工具调用 | 每次调用独立记录，响应按 id 正确合并；底部按工具去重并显示次数。 |
| 工具返回错误 | 工具卡片和底部图标显示异常，正式回复与过程记录不丢失。 |
| 用户默认不展开 | 流式事件不会强制展开过程区，也不会遮挡正式回复。 |
| 用户主动展开 | 实时内容持续更新；完成时保持展开，不自动关闭。 |
| 完成后再次查看 | 过程区仍存在，刷新后能从历史接口恢复相同内容。 |
| 点击工具图标 | 顶部过程区展开并定位到对应工具调用。 |
| 旧历史消息 | 缺少 id/result/status 时不报错、不伪造成功状态。 |
| Partial 与聚合事件同时存在 | 正式回复和 thinking 均不重复。 |
| EOF 但无 done | 页面明确失败并结束 loading，不把临时消息当作已落库结果。 |
| 参数或结果含敏感/超长内容 | 按规则脱敏、截断并标记，不破坏消息页面和数据库。 |
